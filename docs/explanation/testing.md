# How the repository is tested

The test suite is split by what is being tested, not by how easy the test is to
write. Each layer has one job.

## Unit tests

`self.unitTests` and `perSystem.self.unitTests` route nix-unit suites to
`checks.<system>.nix-unit`. Use them only for pure helpers in `src/lib/`: data
transformations, overlay composition, workflow rendering, and similar functions
whose output can be compared directly.

Do not use unit tests for module option internals or evaluated shell config.
Those assertions are brittle and do not prove that the shell works.

## Dev tests

`self.devTests` evaluates a list of dev shell modules into a real shell, runs
its `shellHook`, and then runs commands in the resulting environment. Tests live
in `tests/dev/<module>.nix` and assert observable effects: files that exist,
content that was written, commands that succeed, and packages that are on
`PATH`.

`flake = true` tests become `checks.<system>.dev-test-<name>` and run in CI.
Leave `flake` at `false` for tests that need bwrap or another
environment-specific tool; they remain available through
`self.lib.<system>.devTests` and are run locally.

## Checks and NixOS tests

Package assertions, format checks, and other build-time behavior use
`perSystem.checks`. Services and containers use `self.nixosTests` and the
container/benchmark helpers. These layers run the real derivations instead of
inspecting config.

## Generated files

Some repository files generated by dev modules are paired with a drift check.
The `workflows` dev module writes `.github/workflows/*.yaml` and exposes a
`workflows` passthru check; `nix flake check` fails when a committed workflow no
longer matches its declaration.
