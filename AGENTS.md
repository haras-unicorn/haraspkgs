# AGENTS.md

Common Nix library and packages I use across my repositories.

## Repository conventions

- **Every `.nix` file except the top-level `flake.nix` is a flake-parts
  module.** This includes library code, tests, and repo tooling. Do not create
  plain Nix helper files that the flake imports behind the module system's back.
- **A Nix module that owns asset files lives in a folder named after itself.**
  Use `<name>/default.nix` for the module and keep its assets beside it. For
  example, `src/packages/freetoken/default.nix` owns its `pyproject.toml` and
  lockfile. Do not leave a sibling `<name>.nix` next to a `<name>/` asset
  folder.
- **Do not monkey-patch `flake.nix` to filter directories out of
  `import-tree`.** Import everything under `src/`; import `tests/` too when it
  exists. Small duplication is acceptable if it keeps the module graph obvious.
- **Keep modules self-contained.** `src/flake/overlays.nix` owns
  `self.overlays`, `src/flake/machines.nix` owns `self.machines`, and so on.
  Helpers can live in the module that needs them; do not centralize unrelated
  helpers.
- **Repository configuration belongs in the dev shell.** Generate `.gitignore`,
  `.gitattributes`, `.github/workflows/*.yaml`, `LICENSE.md`, and
  `CODE_OF_CONDUCT.md` through dev modules (`file`, `git`, `workflows`,
  `license`, `code-of-conduct`) rather than maintaining them only by hand.
  Committed copies are mirrors for tools that run before the shell; the dev
  modules are the source of truth. Hook scripts are generated into the store and
  activated by the git wrapper, not committed.
- **Tool configuration that does not need a repository file stays in the
  shell.** EditorConfig and CSpell configs are delivered through global
  `bwrap.files`; Prettier, Markdownlint, and markdown-link-check configs are
  store paths passed on the command line. Do not commit `.editorconfig`,
  `.helix/`, `.prettierrc.yml`, `.prettierignore`, `.markdownlint.json`,
  `.markdownignore`, `.markdown-link-check.json`, or `cspell.yaml`.
- **GitHub workflows are generated by the `workflows` dev module.** Declare them
  as `workflows.<name>` in a shell, then enter the shell to write
  `.github/workflows/<name>.yaml`. Do not hand-edit the generated files. The
  renderer uses `lib.generators.toYAML`; the `file` module formats the generated
  YAML at shell entry, and the `workflows` passthru check formats a temporary
  copy with raw Prettier to detect drift.
- **Git hooks call the `dev` CLI.** The `git` module registers each hook as
  `cli.commands.hook-<name>`, installs the hook scripts in a store directory,
  and wraps `git` with `core.hooksPath` set through the `GIT_CONFIG_*`
  environment variables. Do not write `.git/config`/`.git/hooks` or reintroduce
  per-hook `dev-git-hook-*` packages.
- **Core flake modules live in `src/flake/`.** They register themselves as
  `self.flakeModules.<name> = { self = false; flake = true; value = ...; }`. The
  base module also carries `_file` and a unique `key`. Direct `import-tree`
  modules get their metadata from `import-tree`.
- **`makeFlake` is the entrypoint.** The top-level `flake.nix` bootstraps `self`
  and calls `self.lib.makeFlake` from `src/flake/default.nix`. Downstream flakes
  call `haraspkgs.lib.makeFlake`.
- **`self` and `flake` are separate flags.** Values use
  `selfLib.lib.selfSubmodule` (or `selfFunctor`) and choose whether they belong
  in the `self` mirror (`self = true`) and the flake outputs (`flake = true`).
  Haraspkgs-provided flake and dev modules use `self = false; flake = true;` and
  are exported through `flake.flakeModules`/`flake.devModules`; downstream
  modules default to `self = true; flake = false;`. The old `_flakeLib` marker
  is gone.
- **This-flake configuration is not exported.** `src/systems.nix`, `src/self/`,
  and the package overlays in `src/packages/` configure this flake only. Shared
  modules live in `src/lib/` and `src/flake/`.
- **Package overlays define packages, not builders.** `src/packages/*` should
  expose derivations (for example `llama-cpp-convert`). Do not expose
  `mkPackage`-style helpers from these overlays.
- **Shell-only overlays live in `src/overlays/shell.nix`.** They use
  `self = false; flake = true;` and are injected into the evaluated shell `pkgs`
  by `src/overlays/dev.nix`, not into the flake's own package set. Use them for
  in-shell helpers such as the `bwrap`-based `makeBubblewrapWrapper`.
- **`makeBubblewrapWrapper.files` values are attrs.** Use
  `{ mode = "ro"|"rw"; source = ...; text = ...; }`. Keys are repo-relative, or
  `~/`-prefixed for `$HOME`. `source` and `text` are mutually exclusive, and
  `rw` cannot use either. Files with `source` or `text` are symlinked under
  `${XDG_CACHE_HOME:-$HOME/.cache}/haraspkgs` and exposed through a read-only
  overlay lower layer so they do not appear as untracked files. Global
  `bwrap.files` are merged into every wrapper by the shell overlay; explicit
  wrapper files win. In `NIX_BUILD_TOP` and on non-Linux the wrapper writes the
  files into the checkout, runs the command directly, and still cleans up, so
  wrapper tests can stay `flake = true`.
- **Parametrized lib entries are functions.** `self.lib.containers` and
  `self.lib.benchmarks` map each declaration to `args: ...`, forwarding `args`
  to the declaration's `value`. Keep `args` out of the declarative entry so
  callers (such as dev commands) can supply per-invocation arguments.
- **Repo development tooling lives in `src/self/`.** That includes the docs
  build, the `dev` CLI, and this repository's workflow declarations. Dev-shell
  modules live in `src/dev/`.
- **Dev modules are split consistently across source, tests, and docs.** Each
  `src/dev/<module>.nix` has a matching `tests/dev/<module>.nix` that declares
  `self.devTests` entries and a matching `docs/<quadrant>/dev/<module>.md`. Pure
  library helpers are tested separately in `tests/unit/`; shared dev mechanics
  stay in the top-level dev files (`tests/unit/dev.nix` and the top-level dev
  docs). File fixtures live in `tests/fixtures/`.
- **Dev modules get the flake-parts context and `shellPkgs`.** `self`, `inputs`,
  `specialArgs`, `shellPkgs`, and their keys are module arguments. The shell
  module recreates `_module.args.pkgs` from `config.nixpkgs.system`,
  `config.nixpkgs.config`, and the merged overlay list; the shell-only overlay
  is added and the global-bwrap overlay is appended with `lib.mkAfter`. Use
  `self.outPath` when a check needs a copy of the repository source.
- **Generated text is formatted at shell entry.** `file.<path>.format` writes
  the text first and then runs the registered treefmt configuration from the
  shell hook. Set `format = false` when the exact text matters. Evaluation never
  builds a formatter, so `nix flake check --all-systems` does not need
  formatters for foreign systems.
- **The shared `dev` CLI lives in `src/dev/cli.nix`.** Repo-specific subcommands
  are `cli.commands` entries; `check` and `format` register their subcommands
  automatically. Do not add a second `dev` package outside the CLI module.
- **Prefer consumer inputs; fall back to `selfLib.lib.inputs`.** When a shared
  module needs a flake input, use
  `if inputs ? <name> then inputs.<name> else selfLib.lib.inputs.<name>` instead
  of hardcoding it. This lets a downstream flake override `nixpkgs`,
  `flake-parts`, `nix-unit`, and so on while still working when the input is
  absent. The recursive self filters stop at flake inputs, so reading
  `selfLib.lib.inputs` does not force their outputs.
- **Do not hardcode system triplets.** Generate system-specific outputs with
  `lib.genAttrs config.systems` and read `system`/`pkgs` from `perSystem`. The
  flake's declared `systems` is the single source of truth. The intentional
  exception is the `home-manager` stub in `src/lib/machines.nix`.
- **Shared test fixtures live in `self.lib.test`.** Define
  `self.lib.test = { flake = false; value = ...; };` so tests read it through
  `selfLib.test.value`. `flake = false` keeps it in the self mirror without
  exporting it as a flake output.
- **Unit tests are for library helpers only.** Use nix-unit in `tests/unit/` for
  pure functions in `src/lib/`. Do not unit-test module option internals,
  package builders, or generated shell config; cover those with dev tests,
  checks, or NixOS tests.
- **Dev modules are tested through `self.devTests`.** Prefer observable effects
  (files written, commands that run, packages on `PATH`) over assertions on
  evaluated config attrs. Wrappers fall back to direct execution with cleanup in
  build sandboxes and on non-Linux, so wrapper behavior can be tested with
  `flake = true`.
- **Unit tests go through `self`.** Put system-agnostic suites in
  `self.unitTests` and per-system suites in `perSystem.self.unitTests`. The
  unit-tests module routes them to nix-unit and adds `checks.<system>.nix-unit`,
  so `nix flake check` runs them.
- **Dev shell behavior is tested with `self.devTests`.** Each test evaluates its
  `modules` into a shell, runs the shell's `shellHook` in a writable copy of
  `self.outPath`, and runs the test commands. `self = true` tests live in
  `self.lib.devTests`; `flake = true` tests become
  `perSystem.checks.dev-test-<name>`. Use `flake = false` only for tests that
  genuinely need a Linux environment or a live bwrap sandbox; CI builds only
  `flake = true` tests.
- **The flake-root overlay is this-flake only.** Keep it in
  `src/packages/flake-root.nix`.

## Documentation

- **README is the basic adoption snippet, a short development cycle, and links
  to the docs and `CONTRIBUTING.md`.** Do not put full contributor or agent
  onboarding material there.
- **`CONTRIBUTING.md` is the short human onboarding path.** Keep it to entering
  the dev shell, the source/tests/docs layout, and the commands to run.
- **Contributor and agent context belongs in `AGENTS.md`.**
- **Docs follow Diátaxis.** The four quadrants are `tutorials/`, `guides/`
  (how-to), `reference/`, and `explanation/`.
- **Guides and reference describe patterns, not individual packages.** Use the
  overlay and package patterns instead of a page per package.
- **`docs/introduction.md` is the top-level outline.** It explains the docs
  structure, the conventions, and what lives in the repository.
- **Adoption is split across the how-to guides.** `guides/adoption.md` only
  covers the bare minimum for adding `haraspkgs`; each feature gets its own
  guide, and each reference page is scoped to one API.

## Releasing

- **Release metadata is owned by release-please.** `.release-please-config.json`
  is hand-maintained; `VERSION.txt` and `.release-please-manifest.json` are
  updated by the release PR. Do not edit the generated version files while
  developing.
- **Use `initial-version` for the first release.** Do not leave `release-as` in
  the config; it persists and forces the same version on later releases.
- **Tags come from release-please.** The `release` workflow opens a release PR
  on every push to `main`. Merge it without editing its title; the same workflow
  then creates the `vX.Y.Z` tag and GitHub release. Do not tag manually.
- **Update adoption references after a release.** Keep the README and
  `docs/guides/adoption.md` examples on the latest tag.
- **Prerequisites:** `RELEASE_PLEASE_TOKEN` and `CACHIX_AUTH_TOKEN` repository
  secrets, GitHub Pages configured with source "GitHub Actions", and the
  `haras`/`haras-releases` Cachix caches.
